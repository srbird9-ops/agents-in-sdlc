我们先为项目添加了一项小功能，但更复杂的变更需要更完善的流程。GitHub Copilot app 支持组织现有的工作流程，帮助我们用正确的方法构建所需功能。从本课程开始，你将遵循典型的代理驱动开发流程：从 issue 开始实现新功能，确认代码有效且功能行为符合预期，最终将变更成功合并到项目中。

> [!NOTE]
> 后续处理该功能时，请继续使用同一个会话。通常，不同类型的文件会使用不同会话或 PR；为了让我们专注于核心概念，本工作坊会简化这部分流程。

本课程将学习如何：

- 从 GitHub issue 启动新的代理会话。
- 在 **Plan** 模式中确定需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续处理此功能时，你还将更新仓库说明、自定义现有的 `quality-checks` 技能、添加 MCP 验证、创建 QA 代理，并打开功能 PR。

## 场景

Tailspin Toys 的游戏目录不断增长，访客需要按类别和发布商筛选游戏。待办 issue 描述了这项功能，但多个类别如何组合等细节需要在编码前达成一致。你将使用 Plan 模式解决这些问题，然后授权执行范围明确的实现任务。

## 背景

在开发流程中引入 AI 编码代理，并不会改变基本原则；事实上，这些原则变得更加重要！大多数开发者遵循的流程大致如下：

1. 打开已创建的 issue，查看需要完成工作的详情。
2. 为需要构建的内容制定计划。
3. 编写并审查代码。
4. 运行测试验证代码。
5. 手动验证新功能。
6. 创建拉取请求（PR）。
7. 代码通过审查且持续集成成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程与上述步骤大同小异。

遵循这套标准流程，可以确保 AI 生成的代码满足既定要求，并接受与手写代码相同的审核。

## 会话模式

**会话模式**决定代理具有多大的自主权。你可以通过提示框下方的下拉列表设置模式，并随时更改：

- **Interactive**：你与代理协作。代理提出变更建议，并等待你的输入后再继续。
- **Plan**：代理先制定计划。你审查并批准计划后，代理才会执行。
- **Autopilot**：代理完全自主工作，包括编写代码、运行测试并持续迭代，无需等待输入。

先在 Plan 模式中审查计划，再使用 Autopilot 实现计划。

## 从 issue 启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏 **Sessions** 下选择 Tailspin Toys 仓库文件夹，然后在仓库顶部导航中选择 **Issues**。打开已有的预置 issue **Allow users to filter games by category and publisher**。无需再创建新的 issue。
2. 选择 **New session**，再选择基于更新后 `main` 的 **new working tree**。

    ![GitHub Copilot app 的 issue 视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认 issue 已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让代理运行 `node --version` 和 `npm --version`。如果这些命令在终端中能运行，但在会话中不能运行，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重试失败的操作和检查；不要仅仅因为代理找不到 npm 就重新安装它。

## 规划筛选功能

规划让你可以在 Copilot 编写代码前审查实现方案。由于会话从 issue 启动，Copilot 已获得功能请求的上下文。请发送：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照 issue 中的验收标准审查计划。确认计划涵盖类别和发布商筛选、无障碍控件、数据访问变更和测试。讨论尚不明确的行为，例如多个类别如何组合，或没有游戏符合条件时应如何处理。

计划应使用项目现有工具运行 lint、单元测试、E2E 测试和类型检查。将范围限定为实现和测试筛选功能；完成质量工作流后再创建 PR。批准前先要求修改计划中的不足之处，并留好 issue URL 和已达成一致的说明，供之后验证时使用。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中的等效选项。确认活动模式指示器显示 **Autopilot**，不要假设批准计划时模式会自动切换。

Copilot 会开始实现功能，按照既定计划逐步推进、生成代码并运行测试。

> [!NOTE]
> 批准后可能立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再将检查视为已完成。只停止你自己启动的服务器。

## 审查并验证实现

与其他代码一样，生成的代码也需要在合并前审查。现在审查代码并运行网站，确认一切正常。

1. 打开 **Changes**，检查筛选实现和测试。
2. 将结果与 issue 和已批准的说明进行比较，包括多个类别及发布商的组合。确认变更遵循现有仓库说明。
3. 检查 lint、单元测试、E2E 测试和类型检查的输出。跳过的检查不能算通过。
4. 接受实现前先解决失败项，并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，也可能复用本地服务器；请确保被测服务器属于此工作树，而不是上一课的服务器。

## 体验新功能

代码看起来没问题，但能否正常运行？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示，请 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别，确认结果与类别相符。清除筛选后，选择一个发布商并确认结果与发布商相符。
4. 同时设置类别和发布商筛选，并对照 issue 和已批准的计划检查结果。如果支持多个类别，请验证约定的组合行为。
5. 测试一个没有匹配游戏的组合，检查空状态。清除或重置筛选条件，确认游戏列表恢复完整。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器，并关闭浏览器画布：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

- 从 GitHub issue 启动新的代理会话。
- 在 **Plan** 模式中确定需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查了代码。
- 在浏览器画布中手动验证了功能。
